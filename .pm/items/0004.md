Outcome: (1) each service exposes on its INTERNAL management port (9090, never the public port) a fault interface: crash (exit non-zero on demand or on the next request), latency (delay responses by a bounded number of milliseconds), and a reset; the interface requires the shared secret EXAMPLE_TOKEN (already a required binding) and refuses without it, so an unauthorized caller is denied and the denial is observable; every fault is bounded (latency capped, crash loops limited by the container restart policy, no unbounded resource growth) and shows a symptom the health endpoint reports honestly (not-ready with a reason); (2) isolated fault controls that need no cluster privilege: disk-full simulation by filling the files volume to a configured bound, database-down simulation by the api refusing its pool with a named error, and certificate-near-expiry simulation as a documented fixture the campaign can present to Daisy (the spec calls this the certificate-fixture mechanism; if it cannot be simulated safely inside the app, document exactly what the campaign must do instead and do not fake it); (3) each fault records when it was set, by which token holder (never the token), and when it was reset, in the service's own log lines and via a status endpoint on the management port; (4) tests: unauthorized denial; each fault's symptom and reset; latency bound; disk-fill bound; no fault leaks the token; the Compose artifact still validates and the public ports expose no fault interface. DECISIONS (PM, first correction — the builder stopped on two mechanism questions): (a) crash faults are NOT persisted across restarts and need no controller: the crash switch makes the process exit non-zero once (immediately or on the next request); the platform's restart policy (Compose restart: unless-stopped in the artifact; Kubernetes in Daisy's deployment) brings it back, and the campaign observes the restart count and the health endpoint's reason; a 'crash-loop' fault is the same switch armed for N consecutive starts via a bounded counter file on the files volume (N capped, e.g. 3), which is what makes the loop observable and self-limiting; (b) disk-full is a BOUNDED FILL, not quota isolation: the api writes a filler file of a configured size into the files volume, refuses to fill beyond a configured cap or below a configured free-space floor (both required bindings, no defaults), reports the fill in its status and health, and removes it on reset; the README states plainly that this simulates pressure on the shared volume and does not claim quota isolation; (c) certificate-near-expiry stays a documented campaign fixture if it cannot be simulated inside the app. BOUNDARIES are behavioral: no campaign drivers yet (slice 4); no new dependencies; no secrets in files, logs or responses; list touched files in the summary.
